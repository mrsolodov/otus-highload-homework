# Кластер MySQL для веб-проекта

Я выбрал Percona XtraDB Cluster (PXC) и собрал три узла через Docker Compose. Схема `otusapp.requests` повторяет по смыслу таблицу из задания 07: там она была в PostgreSQL, здесь создана в MySQL. Перенос существующих данных не выполняется: предыдущий стенд уже удалён, а для проверки создаются новые записи.

## Как устроен стенд

- `pxc1` запускает кластер, `pxc2` и `pxc3` к нему присоединяются.
- Для каждого узла есть отдельный Docker volume с данными.
- Пароли и самоподписанные сертификаты создаются при запуске и не попадают в Git.
- Внешний порт MySQL не опубликован: все узлы находятся в закрытой Docker-сети.
- Скрипт проверяет состояние Galera, создание базы, чтение записей на всех узлах и запись после остановки `pxc2`.

Это один компьютер с тремя контейнерами. Такой опыт показывает работу кворума и репликации при остановке процесса узла, но не защищает от отказа компьютера. Для реальной эксплуатации нужны разные хосты, резервные копии, внешние сертификаты и отдельная точка подключения приложения.

## Запуск

Нужны Docker Engine с плагином Compose v2, Bash, OpenSSL и около 10 ГБ свободной оперативной памяти. Первый запуск скачает образ Percona и может занять несколько минут.

Из каталога задания:

```bash
./scripts/run-lab.sh
```

На Windows запускать можно из WSL, если в нём доступен Docker (например, через Docker Desktop с интеграцией WSL). Стенд после успешной проверки остаётся запущенным. Для просмотра узлов:

```bash
docker compose ps
```

Чтобы при успешной проверке сразу удалить контейнеры и учебные данные:

```bash
./scripts/run-lab.sh --destroy
```

Если стенд уже был запущен без `--destroy`, для удаления контейнеров и томов можно вручную выполнить `docker compose down -v` в этом каталоге. Команда удалит данные созданной в этом задании базы. Скрипт пишет краткое подтверждение проверки в `evidence/cluster-check.txt`.

## Что проверяется

1. У каждого узла `wsrep_cluster_size=3`, `wsrep_cluster_status=Primary`, `wsrep_ready=ON`, состояние `Synced`.
2. Запись, сделанная через `pxc1`, читается через `pxc2` и `pxc3`.
3. После остановки `pxc2` два оставшихся узла сохраняют Primary Component. Запись через `pxc3` читается через `pxc1`.
4. После возврата `pxc2` на всех трёх узлах видны обе записи.

Команда `run-lab.sh` завершится ошибкой, если хотя бы один шаг не пройдёт. В этом случае контейнеры сохраняются для изучения `docker compose logs`.

## Состояние проверки

Стенд успешно прошёл [проверку в GitHub Actions](https://github.com/mrsolodov/otus-highload-homework/actions/runs/40460149712): три синхронизированных узла, чтение записи на каждом, работа с двумя узлами после остановки `pxc2` и восстановление состава до трёх. Фактический вывод находится в [`evidence/cluster-check.txt`](evidence/cluster-check.txt); в артефакте CI сохранён итоговый вывод скрипта. У GitHub runner было 15 ГБ RAM; на компьютере с меньшим свободным объёмом памяти запуск может потребовать дополнительной настройки Docker.

За основу параметров Compose, сертификатов и проверки кластера взята [инструкция Percona для PXC 8.4](https://docs.percona.com/percona-xtradb-cluster/8.4/docker-compose.html).
