# Балансировка веб-приложения через Nginx

В этой работе я собрал небольшой стенд из четырёх ВМ: один балансировщик `lb` и три фронтенда `web1`, `web2`, `web3`. На фронтендах работают Nginx, статическая страница и простое Python-приложение под uWSGI. Балансировщик направляет запросы на фронтенды и показывает два алгоритма распределения трафика.

Сначала я подготовил инфраструктуру в Yandex Cloud через Terraform. Запустить её не удалось: заявку на увеличение квоты vCPU отклонили, а действующего лимита не хватало для четырёх машин. Поэтому проверил ту же схему локально в VirtualBox. ВМ создаёт Vagrant, настройку выполняет тот же Ansible playbook, который подготовлен для облачного варианта.

## Схема стенда

| ВМ | Локальный IP | Что делает |
| --- | --- | --- |
| `lb` | `192.168.77.10` | Принимает запросы и балансирует их через Nginx |
| `web1` | `192.168.77.11` | Nginx, статика, Python/uWSGI |
| `web2` | `192.168.77.12` | Nginx, статика, Python/uWSGI |
| `web3` | `192.168.77.13` | Nginx, статика, Python/uWSGI |

В задании нужны четыре ВМ и как минимум два фронтенда. Я сделал три фронтенда, чтобы все четыре ВМ участвовали в работе стенда и можно было наглядно проверить поведение при отказе одного узла.

Запросы на `/rr/` распределяются по очереди. Для `/hash/` настроен consistent hash по параметру `key`: запросы с одним ключом отправляются на один фронтенд, пока состав доступных узлов не меняется. По заголовку `X-Frontend` видно, кто обработал запрос, а `X-Balancing-Mode` показывает выбранный режим.

## Как запускал

На Windows нужны Vagrant и VirtualBox. Из PowerShell в каталоге этой работы:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\run-local-lab.ps1"
```

Скрипт проверяет `Vagrantfile`, поднимает и настраивает четыре машины, проверяет оба режима балансировки, временно останавливает Nginx на `web2`, затем восстанавливает его. В конце удаляет стенд. Пошаговые команды для ручного запуска и диагностики оставил в [LOCAL-LAB.md](LOCAL-LAB.md).

В каталоге `ansible` лежат playbook, статический inventory для Vagrant, шаблоны конфигурации Nginx, приложение и systemd-служба. Каталог `terraform` содержит подготовленный облачный вариант. Его команды вынесены в [CLOUD-LAB.md](CLOUD-LAB.md); этот вариант я не запускал из-за квот.

## Что получилось

Локальная проверка завершилась с `Checks passed`:

- Девять запросов к `/rr/api/health` получили HTTP 200; ответы последовательно пришли от `web2`, `web3` и `web1`, затем цикл повторился.
- Шесть запросов к `/hash/api/health?key=otus` получили HTTP 200 и все попали на `web3`.
- Страница `/rr/` вернула HTTP 200 и HTML фронтенда `web2`.
- После остановки Nginx на `web2` шесть запросов получили HTTP 200 от `web1` и `web3`.
- После запуска Nginx на `web2` он снова появился в ответах балансировщика.

Полные значения ответов сохранены в [local-lab-results.json](evidence/local-lab-results.json), а вывод проверки — в [local-lab-run.txt](evidence/local-lab-run.txt). Из опубликованного журнала убраны служебный заголовок PowerShell с именем пользователя и абсолютные пути на моём компьютере; результаты команд сохранены.

## Удаление стенда

Скрипт завершил `vagrant destroy -f` с кодом `0`; в консоли было показано удаление `lb`, `web3`, `web2` и `web1`. За дальнейшую работу локальных ВМ ресурсы компьютера не расходуются.
